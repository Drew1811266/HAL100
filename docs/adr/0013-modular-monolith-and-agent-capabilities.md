# ADR-0013：模块化单体、应用边界与 Agent 能力架构

- 状态：已接受
- 日期：2026-08-20
- 关系：补充并校准 ADR-0001、ADR-0004 与 ADR-0007；不改变 ADR-0002 的 Gateway 数据面、ADR-0008 的 Sidecar 隔离和 ADR-0009 的 WebView 生命周期决策

## 背景

HAL100 在迭代 0—11 已经形成模型管理、推理运行时、Gateway、软件接入、Usage、受控 Agent 和环境诊断等完整纵向闭环。现有 `hal100-core`、`hal100-infra`、`hal100-platform`、`hal100-protocol` 与 Tauri 桌面层成功建立了最初的权限和进程边界，但随着功能增长出现了新的结构压力：

- `hal100-protocol` 同时承载跨进程契约、桌面 DTO 和部分领域词汇。
- `hal100-core` 仍然很薄，部分应用协调和业务判断分布在 Infra 与桌面层。
- `hal100-infra` 同时包含数据库、HTTP、进程适配器以及部分确定性管理流程。
- 桌面 `AgentService` 直接协调数据库、Gateway、模型运行时、引擎、OpenCode、模型移除、平台启动器与 Sidecar RPC。
- 新增一个 Agent 能力需要同步修改 Rust、Sidecar、RPC、工具策略、界面和测试，现有逐工具 `requires_*` 字段不适合持续扩展。

这些问题的本质是职责与依赖方向，而不是文件行数。HAL100 仍处于早期开发阶段，需要为后续能力增长建立清晰演进路径，同时避免为了未来假设提前建设微服务、通用插件系统或大量空抽象。

## 决策

### 1. 保持模块化单体

HAL100 继续使用一个长期驻留的 Tauri/Rust 主进程、一个本地 Gateway 数据面、一个 SQLite 数据库以及按需运行的推理进程和 Agent Sidecar。当前不拆分微服务，不引入独立系统守护进程、通用插件框架或跨进程事件总线。

模块是否需要拆分，以职责、变化原因、依赖方向和独立可测试性判断，不设置源文件行数、目录文件数或测试数量上限。代码量随产品能力增长是正常结果；只有无关能力被迫共同变化时才形成架构问题。

### 2. 采用七个业务上下文

| 上下文 | 拥有的长期职责 |
| --- | --- |
| Gateway 数据面 | 本地认证、协议入口、流式转发、取消、路由快照、后端调用和 Usage 捕获 |
| 模型生命周期 | 模型目录、远端目录、下载、导入、校验、所有权、移除和存储恢复 |
| 推理运行时 | 托管引擎、外部后端、进程状态、健康检查、切换、排空和后端能力 |
| 软件接入 | OpenCode、通用客户端及未来专用客户端的检测、配置计划、所有权和回滚 |
| Agent | 能力授权、Provider、任务运行、工具调用、操作计划、取消和结果校验 |
| Usage 与审计 | 精确用量、保留策略、审计事件、错误归类和安全查询 |
| 平台与桌面适配 | Keychain、原生确认、文件选择、系统探测、Sidecar 启动、托盘、窗口和 Tauri IPC |

SQLite 继续是唯一持久化事实源，但表、查询和迁移具有明确的逻辑所有者。上下文之间通过应用用例、稳定快照或显式结果协作，不通过任意 SQL、共享可变前端状态或隐式文件约定耦合。

### 3. 明确数据面与控制面

Gateway 请求热路径属于数据面：

```text
客户端 → Gateway → 内存路由快照 → 推理后端
                    └→ Usage单写入队列
```

模型、后端、软件接入、Agent 和桌面设置属于控制面：

```text
React → Tauri适配 → 应用用例 → 领域策略/确定性管理器
                              └→ 更新Gateway路由快照
```

数据面不得因本次架构演进引入 React 状态、Agent 状态、Keychain实时读取、SQLite查询、模型目录扫描或配置文件检查。控制面通过短时更新内存路由和认证快照影响数据面。

### 4. 目标依赖方向

- React 只通过明确的桌面 API 访问系统能力，不直接成为事实状态或权限主体。
- Tauri command 是外部适配器，负责 DTO 接收、原生确认、调用应用用例和错误映射；确定性规则不以 WebView 输入为权威。
- 应用用例负责跨领域工作流和事务边界，描述“完成什么”，不承担具体 HTTP、SQLite、Keychain、文件选择器或子进程实现。
- `hal100-core` 逐步收纳领域策略、授权规则、能力模型和可独立测试的应用边界；不要求一次性迁移全部既有类型和管理器。
- `hal100-infra` 提供 SQLite、HTTP、Gateway、下载、文件和进程等适配实现。已经稳定的 Manager 只在对应能力被修改时渐进迁移，不进行大爆炸重写。
- `hal100-platform` 继续提供凭据、硬件与 Sidecar 启动等平台实现，平台细节不进入领域策略。
- `hal100-protocol` 长期只拥有跨 Tauri、HTTP 或 Sidecar 边界的序列化契约。现有兼具领域含义的 DTO 保持兼容并按触达迁移；新的纯内部业务类型优先进入 Core。

迭代 12 暂不新增 `hal100-application` crate。先在现有 Core 中验证领域策略与应用边界；当应用用例形成稳定、独立且足够大的依赖集合时，再用新的 ADR 决定是否拆出单独 crate。

### 5. Agent 使用可扩展能力模型

Agent 的长期扩展单位是能力，而不是不断增加独立布尔字段。内部能力定义至少包含：

- 稳定能力标识。
- 风险等级与数据敏感级别。
- 前置能力或必需读取步骤。
- 是否只读、生成计划或产生确定性执行。
- 是否要求原生确认。
- 参数约束、结果约束和对应执行边界。

迭代 12 为现有 10 个工具建立统一的内部能力注册和任务允许集合，但继续通过适配器保持 Agent RPC v3 不变。计划中的模型搜索与下载能力进入实现时，再以独立协议决策评估 RPC v4；如果升级，优先使用能力集合或步骤列表，避免继续扩展逐工具布尔字段。

Agent 运行协调、Sidecar 进程/RPC、能力策略、确定性操作计划和 Provider 会话是不同变化轴。它们可以由一个稳定的 Agent 外观协调，但不能继续依赖同一个类中的隐式共享逻辑。只为真实变化边界建立少量端口，不为每个 Manager 方法创建机械包装接口。

### 6. 前端采用渐进式业务切片

前端长期按相同业务上下文组织页面、组件、查询与桌面 API。迭代 12 只以 Agent/环境诊断作为第一条参考切片，不一次性迁移全部页面和样式。后续修改模型、后端、软件接入、Usage 或设置时，再沿同一模式迁移对应功能。

浏览器预览是桌面 API 的只读适配实现，不是第二套业务逻辑；它不得模拟成功执行真实系统操作。

### 7. 采用渐进迁移

- 每次迁移保留可运行开发版和既有纵向闭环。
- 先用特征测试固定现有行为，再移动职责，最后清理旧入口。
- 新能力必须进入目标边界；旧能力只有在被修改或阻碍新能力时才迁移。
- 迁移期间允许兼容外观和适配层存在，但必须标明事实状态源和最终所有者。
- 不同时重写 Gateway 热路径、数据库 schema、Agent RPC 和前端信息架构。
- 架构验收关注依赖和行为，不使用行数、文件数、接口数或测试数量作为质量代理。

## 迭代 12 参考切片

迭代 12 以“应用边界与 Agent 能力架构”为交付目标：

1. 建立业务上下文地图和依赖规则。
2. 为现有 Agent 工具建立内部能力模型、风险与前置关系。
3. 分离 Agent 任务协调、Kernel/RPC、能力策略、操作计划和 Provider 会话职责。
4. 为 Kernel执行、环境只读信息、确定性计划和Provider会话建立少量稳定边界。
5. 让桌面层成为依赖装配、原生确认与 IPC适配入口。
6. 以 Agent/环境诊断建立首个前端业务切片，其余页面按需渐进迁移。

## 非目标

- 不新增用户可见功能。
- 不改变 Gateway 请求生命周期和性能策略。
- 不升级 Agent RPC、Tauri IPC或 SQLite schema。
- 不建设微服务、通用插件系统或多数据库架构。
- 不全面重写所有 Infra Manager。
- 不为了结构整齐一次性拆分所有前端页面或 CSS。
- 不处理签名、公证、安装包、发售和正式分发。

## 验证与完成条件

- 现有 Agent 能力均能映射到唯一的内部能力定义，未知能力故障关闭。
- 能力风险、前置步骤、计划与确认策略可以脱离 Tauri、SQLite、Node和真实模型独立测试。
- Agent任务协调不再直接承担全部数据库、Gateway、引擎、OpenCode、模型移除和Sidecar协议细节。
- 原生确认取消、计划过期/替换、伪造关联、任务取消、临时凭据/路由/目录回收和云端不回退语义保持不变。
- Agent RPC v3、10个工具、Tauri IPC、SQLite schema v7、Gateway热路径和浏览器预览权限保持兼容。
- `pnpm check`、生产构建、Gateway契约测试和快速后台稳定性检查通过。
- 文档明确记录已迁移职责、过渡适配层和下一步所有者。

## 后果

- 迭代 12 会优先改善未来修改路径，而不是直接增加用户功能。
- 代码总量和文件数量可能增加，但跨领域隐式依赖应减少，核心策略可以更便宜地测试。
- 一段时间内新旧组织方式会并存；渐进迁移记录是完成条件的一部分。
- 新增模型搜索/下载、模型修复或更多软件接入时，应先复用参考切片验证边界，再决定是否产生新的抽象或 crate。
