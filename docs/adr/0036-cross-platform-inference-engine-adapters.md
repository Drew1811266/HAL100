# ADR-0036：跨平台多引擎适配器边界

- 状态：已接受
- 日期：2026-08-26

## 背景

HAL100未来需要覆盖macOS、Windows和Linux。当前`LlamaCppManager`已经拥有可靠的固定供应链、
状态复验和受控生命周期，但外部后端类型同时混合了具体引擎、通信协议和所有权；个人运行方案
又在管理器和SQLite中把引擎固定为`llama.cpp`。继续按这种结构增加MLX-LM、SGLang、OpenVINO
等实现会产生组合枚举、错误的平台推断和不清晰的执行权限。

## 决策

1. 协议层独立定义引擎身份、所有权、本机/远端部署位置、Gateway协议、目标平台、硬件加速器和模型格式。所有持久化
   引擎身份使用Rust固定白名单；任意字符串、路径、命令或环境变量不能成为受管引擎身份。
2. Infra以对象安全的`InferenceEngineAdapter`作为HAL100托管本机引擎边界，统一描述能力、读取
   状态和容量，并提供一次性安装/移除计划及启动、停止、强制切换生命周期。
3. 现有`LlamaCppManager`成为第一个适配器。当前描述符只声明已经实现和验证的Apple Silicon、
   Metal、GGUF与OpenAI兼容路由；枚举中存在未来身份不表示产品已经支持。
4. 现有`BackendKind`和桌面线协议暂时保持兼容，但提供确定性维度映射。外部后端的部署位置不能
   从引擎类别猜测，必须由经过校验的实例URL派生。后续逐步把具体引擎身份
   与OpenAI/Anthropic/Ollama协议分开，避免破坏现有配置和Gateway热路径。
5. SQLite schema v11迁移并保留v10运行方案，将`engine`约束扩展为固定未来身份白名单。运行方案
   只能由当前注册适配器保存；读取到没有适配器的身份时必须判定不可用，不能交给其他引擎执行。
6. Pi只读取Rust整理的有界能力与现实状态，并提出引擎/方案意图。适配器选择、供应链、参数、
   平台权限、确认和执行继续由Rust拥有。

## 平台策略

- llama.cpp作为macOS、Windows、Linux的通用保底方向，但每个平台资产和加速器必须独立验证。
- MLX-LM只作为Apple Silicon优化实现，不伪装为跨平台引擎。
- vLLM、SGLang和TensorRT-LLM优先作为Linux外部服务适配；获得托管权前需独立供应链与隔离设计。
- OpenVINO面向未来Windows/Linux Intel设备；MLC LLM保留为跨平台候选。
- Ollama优先完善为三平台外部本机适配器，是否托管其安装生命周期另行决策。

## 影响

- 运行方案管理器不再持有`llama.cpp`身份常量，而从已注册适配器读取受控身份。
- 新增引擎不需要修改Pi权限模型或让模型生成任意启动命令。
- 当前产品行为不变：唯一可托管运行的用户引擎仍是Apple Silicon llama.cpp。
- 数据库升级到schema v11，但不涉及应用签名、公证、安装包、自动更新或正式升级流程。

## 非目标

本决策不在当前迭代实现Windows/Linux应用、不下载新的引擎、不引入插件执行、不自动选择未经
实测的参数，也不承诺枚举中的全部引擎已经可用。
