# ADR-0021：Rust拥有的可恢复 Agent任务架构

- 状态：已接受
- 日期：2026-08-24
- 决策范围：HAL100内置 Agent、Pi Agent Core编排、配置任务生命周期和评测基线
- 关联：[ADR-0006](0006-pi-agent-core.md)、[ADR-0013](0013-modular-monolith-and-agent-capabilities.md)、[ADR-0017](0017-controlled-operations-observation.md)

## 背景

HAL100内置 Agent已经具备18项固定工具、一次性写计划、原生确认、确定性执行和执行后诊断。
当前运行链仍以一次性提示词为中心：Rust使用关键词推断所需工具，Sidecar通过长系统提示和强制
工具顺序驱动Pi，任务生成一个计划后结束。用户确认执行后，Rust虽然重新诊断，但同一Pi任务
不会继续验证目标是否真正完成。

这种实现适合建立最初安全闭环，但不足以持续支持安装、配置、排障、重新配置和断开等多阶段
任务。单纯增加提示词、工具数量或模型规模不能解决任务所有权、确认暂停、崩溃恢复、证据关联
和完成判定问题。

## 决策

### 1. Rust拥有任务，Pi拥有推理回合

`hal100-core`定义`AgentTaskSpec`、`AgentTaskState`和`AgentWorkflowDefinition`。Rust拥有任务
身份、目标、期望状态、能力范围、阶段、检查点和终态；Pi Agent Core负责理解用户目标、选择
已经授权的证据能力、解释结构化结果和提出下一步骤。

Sidecar不是任务事实源。Sidecar可以在每个推理阶段后退出，后续由Rust从脱敏语义检查点重建
上下文。Sidecar崩溃不得丢失已经确认的非秘密任务进度，也不得留下可以重新执行的授权。

### 2. 任务以期望状态完成

工作流必须声明：

- 稳定任务类型和目标类型；
- 期望状态与成功判定；
- 允许发送给模型的数据范围；
- 只读、计划、确认、执行、复验和总结步骤；
- 每个检查点允许存在的写计划数量。

“配置文件写入成功”不是配置任务终态。外部Agent配置任务只有在专用适配器重新检测到受管
配置、凭据所有权和协议状态符合预期后才可完成。

### 3. 每个检查点最多一个写计划

一个任务可以包含多个顺序步骤，但任何时刻最多存在一个待确认写计划。安装和配置、配置和
模型切换等不同操作保持独立确认。计划继续在Rust内存中保存、五分钟有效、单次消费；任务
检查点不能恢复、伪造或延长旧计划。

计划过期、应用重启或现实状态变化后，任务只能回到检查或规划阶段重新生成。

### 4. 任务阶段使用显式状态机

```text
Draft → Clarifying → Inspecting → Planning
      → AwaitingConfirmation → Executing → Verifying
      → Completed / Blocked / Failed / Cancelled
```

`Verifying`可以在同一目标尚未完成时回到`Planning`，但终态不能重新打开。未来持久化只允许
保存脱敏任务语义和终态；提示词、回答、凭据、本地路径、原始配置、工具原始结果和确认授权
默认不持久化。

### 5. 工作流注册表是现行任务语义源

迭代31先为18类现有任务建立纯Rust工作流定义。能力工具注册表继续拥有工具风险和前置能力；
任务工作流拥有目标状态、步骤和完成判定。两者职责不同，不合并为一个不断增长的枚举。

当前RPC v9、18项工具、Sidecar协议和桌面行为保持不变。后续结构化意图与可恢复运行链需要
协议变化时单独升级RPC，不以兼容字段把新语义塞入v9。

### 6. 先建立评测合同

`contracts/agent-evals/v1-config-tasks.json`记录配置任务的结构化路由、自然语言改写、所有权
歧义、冲突、越权、计划过期、Sidecar崩溃、确认取消和Provider故障场景。评测分层执行：

1. 清单结构与领域映射；
2. 确定性任务入口与策略；
3. 模拟Provider工具循环；
4. 本地Qwen真实任务；
5. 专用适配器隔离端到端。

没有通过低层确定性评测的能力不能进入真实模型验收。

## 迭代31边界

本迭代先交付领域契约、状态机、工作流注册表、评测清单和架构记录。尚不改变：

- 现有关键词路由和用户可见Agent行为；
- Agent RPC v9与工具Schema；
- Sidecar按任务进程模型；
- 原生确认、一次性计划和确定性执行器；
- 数据库Schema和默认不保存提示词/回答策略。

## 被拒绝的方案

### 继续增加关键词和系统提示

不能形成可恢复任务状态，也会让本地小模型上下文持续被重复规则占用，拒绝作为长期架构。

### 让Pi自行决定最大能力集合

模型不能成为自己的授权主体。Pi可以提出结构化意图，最终能力包络必须由Rust根据用户目标、
目标身份和工作流注册表生成。

### 在原生确认期间长期保活Sidecar

会把UI等待、模型资源、子进程寿命和授权状态绑定在一起，增加崩溃恢复与资源回收复杂度。
采用语义检查点和可重建Sidecar。

### 持久化完整Pi会话

会扩大提示词、回答、工具结果和潜在敏感数据的存储面。任务恢复只保存经过字段白名单约束的
语义状态，不启用Pi文件会话。

### 给Pi开放Shell或任意文件工具

配置继续由专用适配器和确定性执行器完成；本决策不扩大Sidecar权限。

## 后果

- Agent演进单位从“提示词命中一个工具”变为“达到一个经过验证的目标状态”。
- 用户确认后可以在同一任务中继续复验和下一安全步骤，同时保留一次一个写计划的边界。
- Pi本身可以升级、重启或更换Provider，而不拥有任务事实和执行授权。
- 迭代31会增加纯领域代码与评测资产，但不产生用户可见行为变化。
- 本决策不涉及签名、公证、安装包、自动更新、正式升级或发布流程。
