# ADR-0037：宿主能力快照与引擎兼容性判定

- 状态：已接受
- 日期：2026-08-26

## 背景

ADR-0036已经把推理引擎的平台和加速器要求从后端协议中拆出，但系统硬件事实仍由名为
`MacOsSystemProbe`的Apple Silicon专用画像提供，运行方案只能判断引擎是否安装，不能区分
“已安装但当前机器不兼容”。直接为每个引擎加入平台分支会让适配器、界面和Pi获得不同结论。

## 决策

1. 平台层以`NativeSystemProbe`作为统一入口，按需生成不可变`HostCapabilitySnapshot`。快照仅含
   兼容性和容量决策所需的平台、CPU架构、CPU/内存、核心数、模型目录空间和已验证加速器；不
   启动持续采样，不读取序列号，也不保存快照。
2. 协议层固定表达macOS/Windows/Linux、aarch64/x86_64和CPU/Metal/CUDA/ROCm/Vulkan/SYCL/
   OpenVINO。枚举只是受控词汇，只有原生探测和真机证据能把能力放进快照。
3. 每个`InferenceEngineDescriptor`必须同时声明平台、CPU架构和加速器要求。兼容性只有在平台、
   架构均匹配且至少一个加速器相交时成立；任一维度缺失都故障关闭并返回类型化原因。
4. 桌面能力目录、运行方案保存和运行方案激活复用同一纯兼容性函数。界面和Pi不得自行推断
   引擎兼容性，也不能用可执行文件存在、进程名称或环境变量作为GPU证据。
5. 旧`HardwareProfile`和Agent系统摘要暂时由同一快照投影，保持现有桌面/RPC线兼容；未来需要
   给Pi暴露多引擎建议时，应新增受控目录合同，而不是在文本提示中拼接未经验证的数据。

## 当前平台结论

当前唯一实装的完整探测仍是Apple Silicon macOS，快照声明CPU与Metal；当前唯一托管适配器仍是
对应aarch64/Metal/GGUF资产的llama.cpp。Windows和Linux只完成协议表达与探测接口边界，未实现
原生硬件探测、应用运行或引擎资产，因此不得显示为可用。

## 影响

- 运行方案新增“引擎与宿主不兼容”的独立修复原因，避免把安装状态和硬件支持混为一谈。
- 新平台必须先实现并验证原生能力探测，再注册匹配的引擎适配器。
- 没有新增SQLite迁移、Agent工具、后台任务、任意命令执行或发行流程。

## 非目标

本决策不安装Ollama或其他引擎，不实现Windows/Linux桌面应用，不探测未经验证的离散GPU，也不
涉及签名、公证、安装包、自动更新或正式升级流程。
