# ADR-0022：影子意图路由与Pi结构化提案合同

- 状态：已接受
- 日期：2026-08-25
- 决策范围：自然语言任务入口、Pi意图提案、Rust裁决和渐进迁移
- 关联：[ADR-0006](0006-pi-agent-core.md)、[ADR-0013](0013-modular-monolith-and-agent-capabilities.md)、[ADR-0021](0021-rust-owned-agent-task-architecture.md)

## 背景

迭代31已经建立Rust拥有的18类任务、工作流注册表和可恢复状态机，但现行运行链仍由桌面层
关键词直接选择工具。首版20个带提示词场景中只有6个与任务合同完全匹配，且一个对抗提示会被
旧分类器理解成写计划意图。确定性执行器最终仍会限制写入范围，但错误意图会浪费模型回合并
降低用户信任。

直接让Pi返回任意JSON并替换旧路由同样不可接受。模型输出可能包含未知任务、伪造目标、额外
文本、所有权扩大或把Provider选择改成静默回退，因此结构化输出本身不是授权。

## 决策

### 1. 任务入口使用四种显式裁决

Core定义`Task`、`Clarify`、`Reject`和`Unresolved`四种结果：

- `Task`必须包含已通过工作流注册表验证的`AgentTaskSpec`；
- `Clarify`只允许目标缺失、所有权不明和多个写目标三类有界问题；
- `Reject`只表达无效输入、能力越界和所有权越界；
- `Unresolved`表示当前确定性入口无法安全判断，不能自动扩大能力。

裁决对象不保存提示词、解释文本、模型推理过程或工具参数。

### 2. Pi只能提交v1结构化意图提案

`contracts/agent-intent/v1-schema.json`定义Pi未来可提交的最小语义信封。它只包含：

- `schemaVersion`和`disposition`；
- 任务提案的`taskKind`和可选`targetId`；
- 或固定的`clarificationKind`、`rejectionReason`。

合同拒绝额外字段，不接受自由文本理由、工具名、能力列表、Provider、执行参数、确认状态或
授权。Provider模式始终由Rust根据当前本地、云端单次或云端会话状态注入。

### 3. Rust把提案当作不可信输入

`AgentTaskProposalValidator`复验schema版本、精确字段集合、18类注册任务、目标类型、外部Agent
注册ID和资源ID边界，再通过`AgentTaskSpec::new`派生期望状态、数据范围和确认要求。Pi不能直接
选择工具，也不能声明无需确认。

后续接入真实Pi提案时，还必须先执行确定性越权和歧义规则；模型提案与硬规则冲突时，以
`Clarify`或`Reject`为准。

### 4. 先以影子模式运行

迭代32在现行任务启动时调用新路由，只记录枚举化的裁决、任务类型、注册目标和Provider类别；
不记录提示词，也不把结果用于工具选择、计划生成或完成校验。现行Agent RPC v9、关键词路由和
用户可见行为保持不变。

只有固定场景、改写场景和对抗场景达到门槛，并完成真实模型多次运行评测后，才能按任务类型
逐步切换。切换必须保留快速回退到旧执行链的能力，但不能回退安全拒绝规则。

## 被拒绝的方案

### 直接用Pi JSON替换关键词路由

缺少Rust语义验证、迁移对照和真实模型方差数据，拒绝直接切换。

### 让Pi输出工具名或能力集合

工具包络必须由Rust根据任务工作流派生；模型不能成为自己的授权主体。

### 把用户提示词写入日志以分析路由

影子指标只记录固定枚举和注册ID。评测使用仓库固定场景，不扩大生产数据收集范围。

### 用更多宽泛关键词直接替换旧分类器

确定性入口可承担显式模板、硬拒绝和澄清，但自然语言理解最终由受约束的Pi提案补充；不把新的
关键词集合当作最终智能层。

## 后果

- 当前24场景中的20个文本场景可以在不启动模型的情况下验证结构化任务语义。
- Pi获得稳定、低Token、可版本化的意图输出目标，同时仍不拥有授权和执行权。
- 影子路由增加很小的纯字符串判断开销，不启动Sidecar、不访问数据库、不执行写操作。
- 后续需要新增Pi提案RPC阶段、双路裁决、方差评测和按任务灰度切换。
- 本决策不涉及签名、公证、安装包、自动更新、正式升级或发布流程。
